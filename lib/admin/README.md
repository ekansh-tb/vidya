# Owner CMS release contract

- Server-only `VIDYA_ADMIN_CLERK_USER_IDS` is an explicit comma-separated list of verified Clerk user IDs for the relevant deployment instance. Empty configuration closes owner access. Never derive permission from email or parent role.
- Apply additive `0012_owner_cms.sql` through the existing serialized migration runner before enabling the workspace. Schema retains published payloads and review evidence through replacement and archive. No existing learner content/state is deleted.
- Visit `/admin`, import authored content, then import verified outreach snapshot. Both imports are idempotent. The private snapshot records four sent emails (including the verified 8 October Clerk follow-up), three submitted forms, zero approved awards; form dates are record dates when timestamps were not captured. No messages are sent by imports.
- Content JSON editing creates a new immutable identity/revision pair. Record five review dimensions and limitations, then explicitly publish. Archived versions are retained for saved activities. School publication remains constrained by `PUBLISHED_SCHOOL_GRADES` even if owner imports future-grade drafts.
- Integrate `usePublishedActivities(learner, language, savedDraft)` into the LearningHub. `activities` is the current collection; `savedActivity` is the exact saved published/historical revision. Public content cache holds no learner identity or progress. Failed publication service falls back to the reviewed static collection; valid empty publication stays empty. Previously downloaded content remains usable offline.
- Learner support exposes minimal profiles and devices. Revocation requires exact parent, learner and device scope and explicit UI confirmation. No reflection, state body, care notes or tutor transcript endpoint exists.
- AI generation jobs are not enabled. This phase does not configure providers, spend allowances, model guardrails or paid credentials. Support tracks documented requests and awards separately.
- Focused tests cover owner deny/allow, complete review records, immutable publish/history/archive, wrong-level gates, cache failures, and cross-family device isolation. Real SQL tests run only through the dedicated disposable integration database; published fixture rows intentionally persist until that isolated database is destroyed.
